# SVSS — Admin Events API Specification
## Missing Backend Endpoints for the Event Management Module

---

## Overview

The frontend Event Management module is fully built. The following backend endpoints
are required to make it functional. Without these, the admin cannot create events and
customers will see no events to purchase tickets for.

### Why this matters
The entire customer ticket-purchase flow depends on events existing in the database:

```
Admin creates event  →  Customer browses events  →  Customer purchases ticket
POST /api/admin/events     GET /api/events              POST /api/customer/tickets/purchase
                           GET /api/events/:id
```

### 3. POST `/api/admin/events`

**Description:** Creates a new event. Once created, it immediately appears in `GET /api/events`
for customers to browse and purchase tickets for.

**Access:** Protected — `admin` role only

**Content-Type:** `application/json`

**Request Body:**
```json
{
  "name": "Rock Concert 2026",
  "venue": "Grand Arena, Downtown",
  "date": "2026-09-15",
  "time": "19:00",
  "category": "Concert",
  "image": "https://images.unsplash.com/photo-xxx?w=600",
  "description": "An electrifying night of rock music.",
  "zones": [
    { "name": "VIP",      "price": 250, "available": 20 },
    { "name": "Premium",  "price": 150, "available": 45 },
    { "name": "General",  "price": 80,  "available": 120 },
    { "name": "Standard", "price": 50,  "available": 200 }
  ]
}
```

**Validation Rules:**
- `name` — required, non-empty string
- `venue` — required, non-empty string
- `date` — required, format `YYYY-MM-DD`
- `time` — required, format `HH:MM`
- `category` — required, must be one of: `Concert`, `Expo`, `Conference`, `Festival`
- `image` — optional, string URL or `null`
- `description` — optional, string or `null`
- `zones` — required, array with at least 1 item, max 4 items
- `zones[].name` — required, must be one of: `VIP`, `Premium`, `General`, `Standard`
- `zones[].price` — required, number >= 0
- `zones[].available` — required, integer >= 1

**Business Rules:**
- Zone names within a single event must be unique (cannot have two VIP zones)
- After creation, the event is immediately visible in `GET /api/events` for customers
  (assuming `date >= today`)

**Success Response `201`:**
```json
{
  "success": true,
  "data": {
    "id": "64abc123def456789012abcd",
    "name": "Rock Concert 2026",
    "venue": "Grand Arena, Downtown",
```

### 4. PUT `/api/admin/events/:id`

**Description:** Updates an existing event. All fields are optional — send only the fields to update.
Used by the Edit Event page.

**Access:** Protected — `admin` role only

**Content-Type:** `application/json`

**Path Parameter:** `id` — MongoDB ObjectId string

**Request Body** (all fields optional — send only what changed):
```json
{
  "name": "Rock Concert 2026 — Updated",
  "venue": "Grand Arena, Downtown",
  "date": "2026-09-15",
  "time": "20:00",
  "category": "Concert",
  "image": "https://images.unsplash.com/photo-xxx?w=600",
  "description": "Updated description.",
  "zones": [
    { "name": "VIP",     "price": 300, "available": 15 },
    { "name": "General", "price": 90,  "available": 100 }
  ]
}
```

**Business Rules:**
- If `zones` is provided, it **replaces** the entire zones array (not a partial merge)
- `zones[].available` when updated should reflect the remaining seats (not reset to original)
- Updating `zones` does not affect tickets already purchased for this event

**Success Response `200`:**
```json
{
  "success": true,
  "data": {
    "id": "64abc123def456789012abcd",
    "name": "Rock Concert 2026 — Updated",
    "venue": "Grand Arena, Downtown",
    "date": "2026-09-15",
    "time": "20:00",

      { "name": "VIP",     "price": 300, "available": 15 },
      { "name": "General", "price": 90,  "available": 100 }
    ]
  }
```

**Error Responses:**
| Status | Reason |
|--------|--------|

### 5. DELETE `/api/admin/events/:id`

**Description:** Permanently deletes an event. The admin is shown a confirmation modal before
this call is made from the frontend.

**Access:** Protected — `admin` role only

**Path Parameter:** `id` — MongoDB ObjectId string

**Request Body:** none

**Business Rules:**
- Deleting an event does NOT delete existing tickets associated with it
  (tickets already have a denormalized `event` name snapshot)
- After deletion, the event no longer appears in `GET /api/events` for customers

**Success Response `200`:**
```json
{
  "success": true,
  "data": {
    "message": "Event deleted successfully."
  }
}
```

**Error Responses:**
| Status | Reason |
|--------|--------|
| `403` | Not `admin` role |
| `404` | Event not found |

## Zone Availability — Critical Business Logic

The `available` count on each zone is a **live counter** that decrements when a customer
purchases a ticket for that zone.

### How it works

```
1. Admin creates event with:
   zones: [{ name: "VIP", price: 250, available: 20 }]

2. Customer purchases VIP ticket:
   POST /api/customer/tickets/purchase
   { eventId: "...", zone: "VIP", ... }

3. Backend must atomically:
   a. Check zone.available > 0  (reject with 409 if sold out)
   b. Decrement zone.available by 1
   c. Create the ticket record

4. Next call to GET /api/events/:id returns:
   zones: [{ name: "VIP", price: 250, available: 19 }]
```

### Concurrency protection (required)

Two customers can purchase simultaneously. The backend MUST use an atomic operation to
prevent overselling:

```js
// Mongoose example — atomic findOneAndUpdate with condition
const result = await Event.findOneAndUpdate(
  {
    _id: eventId,
    'zones.name': zoneName,
    'zones.available': { $gt: 0 }   // condition: must have seats left
  },
  {
    $inc: { 'zones.$.available': -1 }  // atomically decrement
  },
  { new: true }
)

if (!result) {
  // Either event not found OR zone sold out
  throw new Error('Zone is sold out.')
}
```

**Do NOT** read `available`, check it in application code, then update — that is a race condition.

## Frontend API Call Reference

The frontend calls these functions in `src/api/eventAdminApi.js`:

```js
// GET /api/admin/events
getAdminEventsApi(params)          // → Event[]

// GET /api/admin/events/:id
getAdminEventByIdApi(id)           // → Event

// POST /api/admin/events
createEventApi(payload)            // → Event  (HTTP 201)

// PUT /api/admin/events/:id
updateEventApi(id, payload)        // → Event

// DELETE /api/admin/events/:id
deleteEventApi(id)                 // → { message: string }
```

All responses are unwrapped from the `{ success: true, data: ... }` envelope by the frontend.
The backend must always return that envelope structure.

## Error Response Format

All errors must follow this shape:

```json
{
  "success": false,
  "message": "Human-readable error message.",
  "errors": [
    { "message": "zones must have at least 1 item" }
  ]
}
```

- `message` — required on all errors
- `errors[]` — only present on `400`/`422` validation failures
